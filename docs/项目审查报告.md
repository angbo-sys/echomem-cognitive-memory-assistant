## 三、缺陷与未打通链路

### P0 — 严重缺陷

#### 3.1 STM 无持久化（已关闭）

**位置**：`memory/stm.py`

**原问题**：`ShortTermMemory` 基于 `deque` 实现，进程重启后所有短期记忆丢失。

```python
# memory/stm.py:23
self._messages: Deque[Message] = deque(maxlen=max_turns)
```

**本轮修复**：
- `ShortTermMemory` 新增可选 SQLite-backed 模式：`db_path/user_id/session_id`
- `stm_messages` 保存最近消息，按 `max_turns` 自动裁剪
- `stm_summaries` 保存画像演化 summary
- `clear()` 同时清理内存与持久化状态
- 默认不传 `db_path` 时仍保持原纯内存行为，兼容现有测试与调用方

**验证**：
- `test_sqlite_backed_stm_restores_messages_and_summary`
- `test_sqlite_backed_stm_is_scoped_and_trimmed`
- `test_sqlite_backed_stm_clear_removes_persisted_state`

#### 3.2 向量检索后端未真正打通（已关闭）

**位置**：`memory/vector_store.py`

**原问题**：
1. Chroma 使用 `chromadb.Client()`（内存模式），重启后数据丢失
2. `retrieval_backend` 默认 `"none"`，向量检索始终不可用
3. `MemorySearch` 没有在查询前保证当前 LTM 候选已进入向量索引

**本轮修复**：
- `memory/vector_store.py` 改为 `chromadb.PersistentClient(path="chroma_db")`
- `config/settings.toml` 与 `RetrievalConfig` 默认值改为 `backend="chroma"`
- `MemorySearch.run()` 在查询前 upsert 当前候选记忆到 Chroma
- `backend` 字段改为只有命中可用向量候选时才显示 `"vector"`
- `chroma_db/` 加入 `.gitignore`，作为本地索引产物处理

**验证**：
- `test_chroma_backend_retrieves_and_filters_by_user_id`
- `conda run -n echomem-test python -m unittest discover tests -v`：92 pass

#### 3.3 Cognee 异步操作在同步上下文中未正确处理（已关闭）

**位置**：`memory/open_source_memory.py:CogneeAdapter`

**原问题**：`add_knowledge()` 和 `query_graph()` 是 `async` 方法，但 `related_concepts()` 是同步方法，本地图谱查询未进入主链路。

```python
# open_source_memory.py:537-547
async def add_knowledge(self, texts: List[str]) -> bool:  # async
    ...

async def query_graph(self, query_text: str) -> List[str]:  # async
    ...

def related_concepts(self, query: str, ltm_rows: List[Dict[str, Any]]) -> FrameworkHint:  # sync
    # 未调用 add_knowledge 或 query_graph
```

**本轮修复**：
- `related_concepts()` 在云端搜索不可用时，会对 LTM 文本调用本地 `add_knowledge()`，再调用 `query_graph()`
- 新增 `_run_async_blocking()`，兼容普通同步上下文和已有 event loop 的场景
- 图谱结果合并进 `related_concepts`，并通过 `graph_results/local_graph_search_used` 暴露可观测状态

**验证**：
- `test_related_concepts_uses_local_async_graph_search`
- `conda run -n echomem-test python -m unittest tests.test_open_source_memory -v`：通过

### P1 — 中等缺陷

#### 3.4 检索相似度算法过于简单（已关闭）

**位置**：`memory/retrieval.py`

**原问题**：`lexical_similarity()` 使用空格分词 + Jaccard 相似度，对中文几乎无效。

```python
# retrieval.py:9-13
def _tokenize(text: str) -> set[str]:
    return {t for t in text.lower().split() if t}  # 空格分词，中文无空格

def lexical_similarity(query: str, content: str) -> float:
    q = _tokenize(query)  # 中文会变成整个字符串作为一个 token
    c = _tokenize(content)
```

**本轮修复**：
- `memory/retrieval.py` 新增中文 N-gram tokenization
- `lexical_similarity()` 改为 Jaccard + BM25-like 组合分数
- 保留原函数名，避免影响 `rerank_top_k()` 与现有调用方

**验证**：
- `test_chinese_similarity_handles_semantic_overlap_without_spaces`
- 中文查询“条件概率”对“贝叶斯公式用于条件概率推断”的分数高于无关偏好记忆

#### 3.5 Profile 更新仅依赖正则规则（已关闭基础版）

**位置**：`agent/orchestrator.py:_extract_profile_candidates()`

**原问题**：Profile 候选提取全部基于固定正则表达式，没有语义短语补充。

```python
# orchestrator.py:247-248
goal_match = re.search(r"(?:目标|想要|计划|准备)(?:是|为|:)?(.{2,40}?)(?:[，。；;,、！\n]|$)", text)
```

**原影响**：
- 只能匹配固定句式，自然语言表达无法识别
- 例如"我想考研究生"可以匹配，但"研究生是我接下来的方向"无法匹配
- 置信度固定（0.62-0.72），无法根据语义调整

**本轮修复**：
- `_extract_profile_candidates()` 保留原规则层，避免既有固定句式退化
- 新增 `_extract_semantic_profile_candidates()`，覆盖“方向/目标/主线”“卡住/拖后腿/吃力”“一步一步/拆开讲”“零基础/刚入门”“最近/这阵子/目前”等自然表达
- 新增 `_normalize_profile_value()`，清理前后缀、标点和过长片段
- 语义模式不跨标点抽取，避免一句话包含多个画像事实时串字段
- 当前选择本地结构化语义补强，不默认增加额外 LLM API 调用，保持主对话时延和成本稳定

**验证**：
- `test_semantic_profile_pipeline_handles_natural_paraphrases`
- `test_semantic_profile_pipeline_normalizes_level_and_focus`
- `conda run -n echomem-test python -m unittest tests.test_orchestrator_integration -v`：8 tests OK

#### 3.7 LlamaCloud 和 Cognee Cloud 的 API 端点可能不准确（已复审并修正）

**位置**：`memory/open_source_memory.py:LlamaCloudAdapter`, `CogneeCloudAdapter`

**复审结论**：
1. LlamaParse 官方文档使用 `llama_cloud` SDK，项目方向正确；当前 `echomem-test` 环境已能发现并加载 `llama_cloud`
2. 使用真实云端配置验证：最小文本 `cost_effective + markdown` 解析成功，并在 2026-05-12 云端 E2E 中进入 LlamaIndex Memory 信号
3. Cognee 公共 API `https://api.aws.cognee.ai` 是租户/订阅管理面；真实知识图谱服务应使用 `/api/v1/tenants/current/service-url` 返回的 tenant service URL
4. tenant OpenAPI 显示真实数据端点是 `/api/v1/add_text`、`/api/v1/cognify`、`/api/v1/search`，不是原先推测的 `/api/v1/data`
5. 使用真实 `COGNEE_API_KEY` 和 `COGNEE_BASE_URL` 验证：`add_text`、`cognify`、`search` 均成功

**本轮修复**：
- `LlamaCloudAdapter.parse_document()` 改为 `parsing.parse(upload_file=..., tier="cost_effective", expand=["markdown"])`
- 新增 `LlamaCloudAdapter.parse_text()`，便于最小连通性测试
- `CogneeCloudAdapter.add_knowledge()` 改为 `/api/v1/add_text` + `/api/v1/cognify`
- `CogneeCloudAdapter.search_graph()` 改为 `/api/v1/search`，payload 使用 `query/datasets/topK/onlyContext`
- `deploy_memory_frameworks_local.sh` 和 `check_memory_frameworks_env.py` 加入 `llama_cloud`

**剩余限制**：
- Cognee 本地包初始化仍会输出 LLM 连接探测失败和资源警告；云端 REST 链路不受影响
- UI 尚未提供云端/本地模式开关，仍主要通过配置文件切换

**位置**：`agent/orchestrator.py:_safe_call()`

**问题**：当函数签名不匹配时，静默过滤掉不接受的参数，不抛出异常。

**影响**：调试困难，参数传递错误不会被发现。

---

#### 3.14 `text_search` SQL LIKE 对中文召回能力极弱

**位置**：`memory/ltm.py:133-154`

**问题**：`text_search()` 使用 `content LIKE ?` 做模糊匹配，中文需要完全匹配子串。

```python
# ltm.py:142-143
where = ["content LIKE ?"]
params: List[Any] = [f"%{query}%"]
```

**影响**：如果用户搜索"概率论"，但记忆中写的是"概率论知识"，可以匹配；但如果写的是"贝叶斯公式用于条件概率"，则无法匹配。

#### 3.15 VectorStore.filter 格式不兼容 Chroma（已关闭）

**位置**：`agent/tools/memory_search.py:89`

**原问题**：
```python
vector_hits = self.vector_store.search(
    effective_query, top_k=self.candidate_k,
    filters={"user_id": {"$eq": user_id_filter}} if user_id_filter else None
)
```

Chroma 的 `where` 过滤语法是 `{"user_id": user_id_filter}`，不是 `{"$eq": ...}`。

**本轮修复**：
- `MemorySearch.run()` 改为传入 `filters={"user_id": user_id_filter}`
- 新增测试确认向量召回时只返回指定 `user_id` 的记忆
